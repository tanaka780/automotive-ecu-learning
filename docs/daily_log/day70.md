# Day70

## 実施内容

- `scenario_test/test_uds_diag.py`を新しく作り、整備工場での診断（UDS）の結合テスト（13件）を足した。スキャンツール役が出す要求と応答の組を、送ったサンプル番号と一緒に照合する。条件は、異常中・回復後・消去後（水温115℃→5秒目80℃）、イグニッションOFFの間（10秒目OFF→13秒目ON）、否定応答、`uds_request.txt`が無い場合の4つ

## 確認内容

- 異常中・回復後・消去後に、マスクごとの件数が期待した数になり、消した状態が保存されるか
- イグニッションOFFの間は読み出しにも消去にも応答せず、消えもせず、ONに戻すと応答するか
- 対応していない要求に、決めた理由の否定応答が返り、記録が消えないか
- わざと誤りを入れたC側のコードで、このテストが落ちるか
- 今あるシナリオ検証が、すべて通ったままか

## 実行結果

| 確認 | 結果 |
| --- | --- |
| `make clean && make` | 警告0件 |
| `test_uds_diag.py`だけを実行 | 13テスト全てOK |
| `make scenario` | 106テスト全てOK（93→106、約134秒） |

わざと誤りを入れた`uds.c`・`uds_tester.c`で`test_uds_diag.py`を動かした結果

| 入れた誤り | 結果 |
| --- | --- |
| 応答の側でイグニッションを見ない | 2件失敗 |
| スキャンツール役が応答を待たずに次を送る | 3件失敗・8件エラー |
| 消去の要求で記録を消さない | 3件失敗 |
| bit5をHISTORYのときだけ立てる | 最初は全部通った。直した後は1件失敗 |
| `uds_request.txt`が無いときに1行ログを出す | 1件失敗 |

bit5の誤りで落ちなかったのは、bit5だけのマスク（`19 01 20`）を、水温を戻した後（HISTORY）にしか送っていなかったため。HISTORYならbit5は立つので、誤りがあっても1件になる。オーバーヒート中（ACTIVE）にも`19 01 20`を送るようにすると、誤りのあるコードでは0件になって落ちた。単体テスト（`test_uds.c`）では、Day69の時点でこの誤りを見つけている。

## 判定

期待通り。

- 異常中・回復後・消去後・OFFの間・否定応答のどの条件でも、送ったサンプルごとの応答が期待と一致し、消した状態も保存された
- 入れた5つの誤りは、テストを1か所直した後、すべて見つかった
- 今あるシナリオ検証93件は通ったままで、足した13件を合わせて106件が通った

## 今回の設計方針

- 要求と応答は、`[TESTER] Request`の行と、その次の`[TESTER]`の行を組にして照合する。応答の行だけを数えると、どの要求への応答かが分からず、順番がずれても気づけない。送ったサンプル番号も一緒に照合する
- `uds_request.txt`が無ければ`[TESTER]`の行が出ないことは、Pythonで確かめることにした。Day69で足さないと決めたのは「変える前と出力が同じか」の比べで、変える前の出力が無いとできない。こちらは「出てはいけない行が出ないか」なので、変える前の出力が無くても確かめられる
- シナリオは、今の「診断コマンド（DTCクリア）」を書き換えず、別のシナリオとして足した。点検コマンドは残しており、受け付ける条件も違うので、1つにまとめると期待結果が混ざる
