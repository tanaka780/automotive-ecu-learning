# Day51

## 実施内容

- Python自動検証（Phase25）の範囲として、検証対象のシナリオ・C側に手を入れる範囲とその順序・テストの枠組みを決めた

## 今回の設計方針

- `sensor_sim`を外から動かして結果を照合できるか、`main.c`から追って確かめた。邪魔になるのは主に3つあった。`ignition.c`の`rand`（`srand(time(NULL))`なので毎回変わる）、ループ終了時にOFFだと`cmd_read_line`が標準入力を待って止まること、1回の実行に約20秒（1000ms×20サンプル）かかること。一方、`config.txt`・`dtc_data.txt`などのファイル名はすべて相対パスなので、一時ディレクトリで実行すれば本番の`dtc_data.txt`を上書きせずに済む
- 最初に検証するシナリオは、設定ファイル異常時のフェイルセーフにした。`[CONFIG]`・`[POST]`のログはサンプルループより前に出るので、イグニッションの乱数に左右されない。Cを一切変えずに期待結果を決め打ちできるのは、このシナリオだけだった
- 電源再投入・故障発生はイグニッションがONにならないとDTCが記録されないので、イグニッションを外から固定する入口がどうしても要る。ここで初めてC側に手を入れる
- `sim/`への移動は、最初「イグニッション固定を追加する時に一緒にやる」としていた。この判断が間違いだと仮定して「Python着手前に先に移動する」案と比べ直したら、移動と機能追加が同じタイミングに重なるのがまずいと分かった。時期はそのままにして、イグニッション固定の直前に移動だけのステップを挟む形に直した。Day49で決めた分離のタイミング（Python自動検証の着手時）は、「検証用のCコードに手を入れる時」と具体化したことになる
- テストの枠組みは`unittest`にした。`pytest`とも比べたが、`pytest`は`unittest`形式のテストをそのまま実行できるので、後から移っても書き直しにならない
