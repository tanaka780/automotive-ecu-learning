# Day78

## 実施内容

- `main`へのpushで動いたGitHub Actionsの最初の結果と、各段階を動かしたシェルを、実行の記録で確かめた
- GitHub Actionsが、パイプの途中の失敗も失敗として扱うようにした。あわせて、どのブランチへのpushでも、画面のボタンからも動くようにし、取り出す部品をNode.js 24向けの版にした
- 作業用のコピーで、単体テスト・ビルド・シナリオのテストをわざと失敗させ、直す前と後のシェルで、失敗が伝わるかを確かめた
- 試し用のブランチ（`ci-try`）にpushして、直した設定がGitHubの上で動くことを確かめた

## 確認内容

- `main`へのpushで、4つの段階（ビルド・単体テスト・シナリオ検証・再生画面のデータ）が通るか
- 各段階が、失敗したときに失敗を伝えるか（単体テストが1件失敗する・コンパイルのエラーがある・シナリオのテストが1件失敗する）
- 直した設定で、GitHubの上でも4つの段階が通り、シェルが`pipefail`付きになり、Node.js 20の注意が消えるか

## 判定

- 最初のpushの緑は、本当に4つとも通った結果だった。ただし、シェルが`bash -e`だったので、単体テストとビルドの段階は、失敗しても緑になる作りだった。Day77に手元で同じ手順を確かめたときは、`pipefail`付きで動かしていたので、この違いが出なかった
- 直した後は、単体テスト・ビルド・シナリオのどれを失敗させても、失敗が伝わった。直す前は、単体テストとビルドを見逃した。期待通り
- GitHubの上でも、直した設定で4つとも通り、シェルは`pipefail`付きになり、注意も消えた。期待通り
- 最初に試した書き換えは当たっておらず、「失敗しない」は確かめの結果ではなかった。書き換えた数を数え、1でなければ止める形でやり直した
- 再生画面のデータの段階が失敗を伝えることは、Day77で確かめた（パイプを使っていない）

## 今回の設計方針

- シェルはジョブ全体で`shell: bash`と指定する。指定しないとGitHubは`bash -e`で動かし、`make test 2>&1 | tee test.log`のようなパイプでは、途中の`make`が失敗しても、最後の`tee`が成功すれば成功扱いになる。指定すると`pipefail`が付き、途中の失敗も伝わる
- どのブランチへのpushでも動くようにし、画面のボタン（`workflow_dispatch`）からも動かせるようにする
- 設定を直すときは試し用のブランチで確かめ、通ってから`main`に1つのコミットとして取り込む（試した回数だけ`main`のコミットと日報が増えないようにするため）
- 取り出す部品は`actions/checkout@v5`にする（Node.js 24向けで、注意が消えるため）
