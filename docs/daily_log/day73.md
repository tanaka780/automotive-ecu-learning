# Day73

## 実施内容

- 保留中の候補（Watchdog・NVM強化・UDSの拡張・Renodeへの移植など）を比べ、次のテーマにWatchdogを選んだ
- Watchdogの案を「間違いだとしたら」と仮定して別案と比べ直すのを4回繰り返し、そのたびに`fan_ecu.c`・`main.c`・`can.h`を読んで、案の欠陥を確かめた
- ファン制御ECUの処理の停止の検出をPhase32として立て、6つのタスクに分けた

## 今回の設計方針

- 見張るのは、ファン制御ECUの2つの受信のタスク（警告灯データの受信でファンのON/OFFを決める・ゲージデータの受信で水温を持つ）
- 判断のときは「最後に新しい水温を受け取ってから」、送るときは「最後に判断してから」の時間を見て、上限を超えていたらファンをONにする。水温の側は、強制ONと同じく使える水温が決まるまでONを保つ
- 止まったのを見つけたら、リセットではなくまずONに倒す。`fan_ecu_init`は出力をOFFにして始めるので、オーバーヒート中にリセットすると、新しい水温が決まるまでファンが止まる
- リセットするハードウェア役（`mcal_pc/`）はこのPhaseでは作らない。リセットの後もONで起動するなら、その場でONにする対応と同じことを2通りで持つことになる。20秒の実行では、止める・見つける・リセットする・繰り返しを数えるまで確かめきれない
- 見張りは`fan_ecu/`に置く。READMEで`common/`は「2つ以上のECUが使う部品」と決めている
- `state[CAN_MSG_ENGINE_STATUS]`はゲージデータの受信のタスクの中でしか更新されないので、判断のタスクだけを見張る形では、このタスクの停止を見つけられない
- フレームの`timestamp_ms`は`data[]`の外にあり、PCの試験台だけが持つ送信時刻なので、今の時刻との比べには使わない。今の`fan_ecu_sent_after`は同じ送り手の時刻どうしを比べているので、そのままでよい
- 時刻は`main.c`が渡し、`fan_ecu.c`は時計を読まない
- 上限は、水温の古さはゲージデータの途絶の確定（約3秒）より長く、判断の古さは判断の周期（200ms）の数回分にする（値は実装時に決める）
- 止まったときはログを出してファンをONにするだけにし、記録（DTC）は付けない
- タスクを止める仕組みは、`can_fault.c`とは別のファイルとして`sim/`に置く

## 次回やること

- 試験台に、指定した期間だけファン制御ECUの受信のタスクを呼ばない仕組みを足し、今のコードでは、水温が上がってもファンがOFFのまま固まることを確かめる
