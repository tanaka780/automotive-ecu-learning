# Day58

## 実施内容

- 実時間の時計を`src/timer.c`から新規の`src/timer_clock.c`へ移し、`timer.c`には周期判定だけを残した
- `src/scheduler.c`のポーリングの待機を、時計と一緒に差し替えられる関数経由に変えた（宣言は`include/timer.h`、実時間の実装は`src/timer_clock.c`）
- 検証用の仮想時計を`sim/timer_clock_virtual.c`として追加した（待たずに時刻を進めるだけ。`timer_clock.c`の代わりにリンクして`sensor_sim_virtual`を作る）
- `src/fan_ecu.c`・`include/fan_ecu.h`で、受け取った水温を、それより後に送られた最初の警告灯データで使えるかを決めてから使うようにした（水温センサの確定・復帰の前後に、差し替え後の25℃でファンをOFFにしないため）
- `test/test_fan_ecu.c`に、確定の瞬間・復帰の瞬間の並びと、送信時刻の一周を確かめる3テストを足した

## 確認内容

- 実時間の`sensor_sim`の動作が変わっていないか（ビルド・単体テスト・シナリオ検証・変更前との比較）
- 仮想時間版が、変更前の実時間版と同じ流れで動くか
- 仮想時間版は、同じ入力なら出力が毎回同じになり、待たずに終わるか
- 仮想時間版の時刻が周期ちょうどに進んでいるか。`can_fault.txt`のDrop期間を1ms単位で境目に合わせ、何秒目にLOST・復帰するかを実行前に計算して比べる
- わざと壊した版で、仮想時間版の全文比較が違いを見つけるか。特に、比較スクリプトでは見つからない周期・登録順の誤り
- 水温センサの確定の前後で、ファンが一瞬OFFになる順番があるか。予想は「警告灯データの送信が確定より前（水温ビット0のまま）で、ファンの判断が水温25℃を受け取った後」のときだけOFFになる
- 水温センサが復帰する流れ（8秒目から78℃）で、ファンがONのままか。78℃は閾値の間なので、故障前の要求（ON）を保つのが正しい
- 直し方の案（案1・案2・案3）が、ずれ方を振っても確定・復帰の瞬間にOFFにしないか。通信の途切れと重ねても誤らないか。実時間版でも復帰の誤りが起きるか
- 案2を入れた本番のコードで、新しいテストが直す前のコードとわざと壊した版で落ちるか。ずらさない並びの出力と既存の結果が変わらないか

## 判定

実時間版の動作は変わっておらず、仮想時間版は予想どおり周期ちょうどに動いた。仮想時間版で見つかったファン制御ECUの誤りは、案2で予想どおり直った。

- 実時間版：時計を差し替えた段階で、ビルド・単体テスト・シナリオ検証の結果はDay57と同じで、比較スクリプトでも8条件とも変更前と一致した。実行時間も約19秒で、実際に待っている
- 仮想時間版：変更前の実時間版と同じ流れになり、同じ入力で出力が全文一致した。Drop期間の境目の4パターンも、実行前に計算したサンプルでLOST・復帰した
- 実時間版との全文の違いは、200ms周期の受信回数の揺れだけだった。これは仮想化で消したかった揺れそのもの
- わざと入れた3つの誤りは、どれも全文比較で違いが出た。ポーリング間隔と登録順の誤りは、比較スクリプトでは見つからない種類
- ファンが一瞬OFFになる順番は、予想どおり実在した。0 < x < yは、警告灯データの送信がサンプル（確定）より前で、ファンの判断がゲージデータの受信（25℃）より後という条件そのもの。最初は「警告灯データの送信を遅らせれば起きる」と考えていたが、遅らせると送信が確定の後になって水温ビット1が届き、ファンの判断もまだ95℃のままなので起きない。Day57の実時間12回で出なかったのは、起きない保証ではなく、この並びがまれだったからと考えられる。実時間でこの並びになるかは確かめていない
- 復帰の瞬間の誤りは、仮想時間版ではずらさない並びでも起き、ONを保つべき78℃でOFFのまま戻らなかった。一瞬で戻る確定の瞬間より影響が大きい
- 案1は予想どおり復帰が直らなかった。案2は確定・復帰とも、どのずれ方でも0件だった。案3は事前に予想を立てずに試し、ずらさない並びでは直ったが、ずれ方を振ると直す前より多くの組み合わせでOFFになった
- 途切れと重ねたときの108通りは、起動直後から止めて、故障前に水温で判断する機会が一度も無かった条件だけ。強制ONの間は水温による要求を更新しない今の決まりどおりに、閾値の間の78℃でOFFのままになった。故障前に水温でONになっていた条件では0件で、案2の誤りではない
- 本番のコードでも試作と同じ結果になり、新しいテストは直す前のコードと、わざと入れた4種類の誤りで落ちた。ずらさない並びの出力は直す前と全文一致し、既存のテスト・シナリオ検証も変わらず通った
- 訂正：復帰の誤りを最初は「ずらさない並びでも毎回起きる」と考えたが、仮想時間版に限った話だった。実時間版では、直す前でも3回とも起きなかった。実時間では200ms周期のタスクのほうが遅れが早く積み重なり、ゲージデータの受信が先になりやすいためと推定している（確かめていない）
- 実験の途中で、水温を変えない条件にも細工用の環境変数を空で渡してしまい、水温が0℃になっていた。その回の「確定の瞬間」と「8条件の全文比較」は捨てて、渡し方を直して取り直した
- 最初の再確認では、実時間版と仮想時間版を同じフォルダで続けて動かしたため、後の実行が前の実行の`dtc_data.txt`を読み込み、`[PERSIST]`の行とDTCの回数が食い違った。フォルダを分けて取り直した結果が上の表

## 今回の設計方針

- `sensor_sim`は実時間のまま残し、仮想時間版は別の実行ファイルにした。デモと既存のシナリオ検証・比較スクリプトは、何も変えずにそのまま動く
- 変更前の基準は、作業中のファイルではなく`67fcc51`を`git archive`で一時フォルダに取り出して取り直した
- 仮想時間版は比較スクリプトにそのまま通せないので、仮想時間版を`sensor_sim`の名前で置いた一時フォルダを使って比べた
- 仮想時間版で同じ入力を何回動かしても同じ結果になるだけなので、タイミングは入力として自分で振る。今回は一時コピーのSchedulerにだけ、タスクごとの最初の実行の遅れを環境変数で渡せる細工を入れて振った（リポジトリのコードは変えていない）。復帰の流れは、同じく一時コピーの`main.c`に、指定した秒から水温を変える細工を入れて作った
- 確定・復帰の瞬間の誤りは、受信側（ファン制御ECU）で直した。水温と「水温が使えるか」を同じメッセージで送るのが根本の直し方だが、メッセージの形とエンジン監視ECUの送信を変えることになり、エンジン監視ECUを変えない方針に触れる
- 最初は「水温より後に送られた警告灯データを待つ」だけの案1を試し、復帰の瞬間が直らなかったので、水温1つごとに1回だけ決める案2にした
- ファン制御ECUのタスクの登録順を入れ替えて、ゲージデータの受信を先にする案（案3）も比べた。ずらさない並びでは直るが、ずれ方を振ると直す前より多くの組み合わせでOFFになった。保証されない順番に頼る直し方なので採らなかった
- 送信時刻は大小ではなく差で比べ、差が半周未満なら後とみなす。大小で比べると、約49.7日で時刻が一周したときに誤る

## 次回やること

- 比較スクリプトとシナリオ検証を仮想時間版で動かすかを決める（全文比較にすれば周期・登録順の誤りも見つかり、シナリオ検証の約2分30秒も短くなる）
- `sim/`で実行中に水温を変えられるようにし、閾値の間でONを保つ流れを仮想時間版で確かめる
- タスクの開始のずれを、検証用に振れる形で残すかを決める（Schedulerのoffsetは、Phase19ではタスクが1個で効果が無いため見送っていた）
- 警告灯データの途絶中に届いた正常な水温で、水温による要求を更新してよいかを決める（起動直後から途絶すると、正常な水温での判断が一度も無いまま確定・復帰を迎え、閾値の間の水温ではOFFのままになる）
