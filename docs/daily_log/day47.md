# Day47

## 実施内容

- cppcheck（`--addon=misra --enable=all --std=c11 -Iinclude`）を`src/`全体に対して実行し、Phase14以降の新規8モジュールの未チェック分を確認した
- `can_diag.c`の`dtc_status_to_str`を`can_diag_dtc_status_to_str`にリネームした（MISRA 5.9対応）
- 新たに見つかったルール21.1（`timer.c`/`scheduler.c`）・8.7（`can_fault.c`）・11.5（`main.c`、当初の対象範囲外だったが追加対応）を検討し、いずれも不採用と判断した

## 確認内容

- 5.9修正後、`make clean && make`が警告0件で通ること
- `make test`で全17ターゲットがPASSし、既存テストへの影響が無いこと
- cppcheck再実行で5.9の指摘が0件になること
- 21.1・8.7・11.5を不採用と判断した理由を、Phase14の既存判断（15.5・21.6・21.10）と同じ枠組みで自分の言葉で説明できるか

## 実行結果

- `make clean && make`：警告0件で通った
- `make test`：全17ターゲットPASS（`test_can_diag`含む、既存テスト内容に変更なし）
- cppcheck再実行：5.9の指摘0件。21.1（2件：timer.c/scheduler.c）・8.7（1件：can_fault.c）・11.5（4件：main.c）はいずれも該当ファイル以外への広がりが無いことを確認した（17.7・10.4・10.8・12.1・18.4は新規モジュール含め0件のまま）

## 判定

期待通り。5.9はリネームで機械的に解消でき、既存のビルド・テストへの影響も無かった。新規3ルール（21.1・8.7・11.5）はいずれもPhase14で確立した「既存設計との衝突」「このプロジェクトの前提との衝突」という判断枠組みでそのまま説明でき、新しい判断基準を追加する必要はなかった。

## 今回の設計方針

- MISRA再チェックは、Phase14で決定済みの12ルールを新規モジュールに機械的に当てはめるだけの想定だったが、実際には新規モジュール固有の新しいルール（21.1・8.7・11.5）が3つ見つかった。コードが増えるほどcppcheckの指摘対象パターン（POSIXマクロ定義・外部リンケージ関数・void*キャスト等）も増えるため、「既存ルールの再適用」だけでなく「新しいルールの採否判断」も毎回セットで必要になることを確認した
- 8.7（`can_fault_is_corrupted`のみ指摘され`can_fault_is_dropped`は指摘されない）から、cppcheckの静的解析は`src/`のみを見ており`test/`からの利用を考慮できていないという分析範囲の限界を認識した。ツールの指摘をそのまま鵜呑みにせず、対象範囲の限界を踏まえて解釈する必要があると気づいた
- `main.c`は当初の対象範囲（新規8モジュール）に含まれていなかったが、cppcheckの全体実行で偶然見つかった11.5について、対応（判断のみ、コード変更なし）が小さくPhase14の枠組みで完結することから、当日中に対象範囲を広げて完了させることにした
