# Day68

## 実施内容

- 診断（UDS）の最小限に着手すると決め、最初の範囲を、エンジン監視ECUが記録の件数の読み出し（0x19 01）と全消去（0x14、groupOfDTCは`FFFFFF`のみ）に1フレームで応答するところまでとした。0x10（診断セッション制御）は入れない
- 要求は`0x7E0`、応答は`0x7E8`で送る。フレームは`data[0]`を長さ（Single Frame）にする。肯定応答は`0x59`・`0x54`、否定応答は`7F <SID> <NRC>`で、NRCは`0x11`（対応していないサービス）・`0x12`（対応していないサブファンクション）・`0x13`（長さの誤り）・`0x31`（`FFFFFF`以外の消去）の4つにした
- 記録の状態とステータスのビットの対応は、bit0（testFailed）をACTIVE、bit5（testFailedSinceLastClear）をNONE以外からつくる。対応しているビットの一覧は`0x21`、DTCの形式は`0x00`（SAE J2012の形式）にした
- 応答するのはイグニッションONの間だけにし、OFFの間は何も返さない。消去に、停車中だけといった条件は付けない
- スキャンツール役は`sim/`に置き、ファイルで指定した時刻に要求を送る。指示のファイルが無い実行では、診断のログを一切出さない
- 標準入力の点検コマンド（`clear`・`clear <センサ名>`）は、メーターECU役・ファン制御ECU役も応答できるようになるまで、今のまま残す
- `include/can.h`・`src/can.c`に、周期のメッセージとは別の診断の要求・応答の枠と、1フレームで送る・読む関数を足した（`can_bus_init`はこの2つの枠も初期化する）
- `test/test_can.c`に、診断の要求・応答の往復、同じフレームを2回受け取らないこと、送れない長さ、使わないバイトの0埋め、1フレームとして正しくない形を受け取らないことのテストを足した
- `include/scheduler.h`で、登録できるタスクの上限を8から10に上げた（診断の応答とスキャンツール役の2つの分）
- `src/main.c`で、タスクの登録を表にしてループで回し、1つでも登録できなければ`[SCHED]`のエラーを出して起動しないようにした

## 判定

期待通り。

- まだどこからも呼ばない段階で、出力と保存ファイルは足す前と一致した。比べ方自体が揺れないことも、足す前どうしの一致で確かめた
- 足したテストは、入れた5つの誤りをすべて見つけた（1つはテストの値を直してから）
- 15.5は、新しく書くECUのコードにも適用しないと決めているので、問題にしない
- 登録を表とループに変えても、出力・保存ファイル・シナリオ検証の結果は変わらなかった
- 上限を超えたとき、変える前は一部のタスクが抜けたまま黙って動き、変えた後はエラーを出して止まった。期待した違いが、両方の向きで出た
- 2.5は採用していないルールで、診断のマクロはこの後のタスクで使う

## 今回の設計方針

- 最初の案を、間違っている前提で4回確かめ直した。下の直した点は、どれもコードを読んで初めて分かった
- ステータスのビット：最初はACTIVEをconfirmedDTC（bit3）にした。しかし`diag_check`は、異常が初めて出た回にそのまま記録する。3回続いたかで確定するのはfaultmgrのほうで、オーバーヒートには確定そのものが無い。記録を「確定した」とは呼べないので、bit3は使わない
- bit5は、最初は「回数が1以上」からつくるつもりだった。しかし回数は`uint8_t`で、256回目に0へ戻る（既知の制約にもある）。そうなると異常中なのにbit5が0になるので、状態区分（消去でNONEに戻る）からつくることにした
- 点検コマンド：最初は、UDSに置き換える方向だった。だが0x14をエンジン監視ECUにだけ送ると、Phase29で保存するようにしたメーター・ファンの記録を消す方法が、ファイルを手で消すことしか無くなる。点検コマンドで3つのECUを全部消すようにしたのは、まさにこれを避けるためだった
- 停車中だけ消去を受け付ける条件は、一度入れてから外した。車速センサが故障と確定すると、車速は停車相当の値に差し替わるので、走っていても「停車中」と判断してしまう
- 診断の要求と応答は、`CanMessageId`に足さない。足すと`CAN_MSG_COUNT`が増え、`persist.c`の`_Static_assert(CAN_MSG_COUNT == 3, ...)`でビルドが通らなくなるうえ、`CanDtcRecord`・`CanMonitor`の配列にも診断のメッセージの分が入る。`CanBus`の中に別の枠として持たせる
- Schedulerの上限（`SCHEDULER_MAX_TASKS`）は8で、`main.c`はちょうど8個を登録している。しかも戻り値を`(void)`で捨てているので、タスクを足しても黙って登録されない。上限を増やし、登録に失敗したら分かるようにする
- 応答のタスクは、1秒周期の`run_sample_cycle`に入れず、短い周期で別に回す。UDSでは、要求から応答までの目安が50ms（P2）
- DTCの形式を`0x00`にしたのは、次の段階（DTCの一覧の読み出し）で、Pコードの番号で返すため
- 今の「OFFのときだけ受け付ける」は、スキャンツールを駐車中につなぐ状況を表したつもりで入れていた（`main.c`のコメント）。実車の整備でも、つないだ後にイグニッションをONにしてから読む
- 1フレームとして正しくない形のフレームは捨てるが、受け取り済みとしては記録する。記録しないと、同じフレームを読むたびに捨て直すことになる
- 要求と応答は同じ形なので、書く・読む処理は1つずつにし、公開する関数は枠を選ぶだけにした
- 最初は8つの登録を`&&`でつないで1つの`bool`にまとめた。しかし`&&`の右側で登録（副作用のある呼び出し）をするのはMISRA 13.5に当たるので、表とループに書き直した
- 表は`const`にしたかったが、cppcheckが`context`を渡すところを11.8（constを外すキャスト）と報告した。キャストはしていないので誤検出と考え、`const`を外した（理由はコメントに書いた）
- 登録できなかったときは、POSTの失敗のように決めてある値で動き続けるのではなく、起動しない。抜けたタスクがメーターの受信だったとしても、黙って動くと途絶の判断がされない
- 上限は、今回足す2つの分だけ上げて10にした。Phase26で4から8に上げたときも、足すタスクの数だけ上げている
