# Day61

## 実施内容

- `src/can.c`・`include/can.h`から、受信した値の表示の関数を外した（表示はメーターECU役の仕事のため）
- `src/meter.c`に、表示の関数をこのファイルの中だけの関数として移した（文面・タグは移す前と同じ）
- `src/can.c`・`include/can.h`の警告灯データの送信を、通信側の型（`CanFaultStatus`）を受け取って詰める形にした（通信の部品がアプリの`FaultManager`を知らないようにするため）
- `src/main.c`で、警告灯データの送信タスクが、`FaultManager`の確定状態から`CanFaultStatus`を作って送るよう配線した
- `sim/can_fault.c`・`sim/can_fault.h`の警告灯データの送信のラップを、同じ引数に合わせた
- `test/test_can.c`の警告灯データの往復テストを、`CanFaultStatus`を渡す形にした

## 確認内容

- 直す前と後で、出力が1文字も変わらないか。再生画面の16場面に、回転数だけが異常になる条件と、3つ同時に異常になる条件を足した18条件で、仮想時間版の出力と終了後の記録ファイルを全文比べる（16場面には回転数の異常が無く、警告灯データの回転数のビットを比べられないため、2条件を足した）
- 再生画面のデータを作り直して、差分が出ないか
- 警告なくビルドでき、既存の単体テスト・シナリオ検証が変わらず通るか
- わざと入れた誤り（`can.c`のビットの取り違え、`main.c`の詰め方の取り違え、`meter.c`の表示の入れ替え）を見つけられるか
- GitHub Pagesで公開した再生画面が、URLで開けるか
- 比べるために何度も動かしても、リポジトリ直下の`dtc_data.txt`を上書きしないか

## 判定

責務のずれを直しても、動きは変わっていない。

- 18条件の出力と記録ファイルが全文一致し、再生画面のデータにも差分が出なかった。表示の文面も、警告灯データのビットも、直す前と同じ
- ビルドの警告は0件で、単体テスト154件・シナリオ検証51件も、直す前と同じくすべて通った。比べるための実行はすべて作業用のフォルダで行い、リポジトリ直下の`dtc_data.txt`は変わっていない
- わざと入れた3種類の誤りは、どれも単体テスト・シナリオ検証・全文比較のどれかで見つかった
- `FaultManager`から警告灯データの中身を作る処理は、以前は`can.c`にあり、`test_can`で確かめていた。今は`main.c`にあり、`main.c`は単体テストにできないので、確かめているのは`make scenario`と全文比較になった。`make scenario`が見ているのは、温度だけの異常と、速度と温度の異常の2条件で、回転数のビットは今回の一時的な全文比較でしか確かめていない
- `include/can.h`に、直す前の書き方のコメント（「FaultManagerのSensorIdの並びに合わせる」）が1か所残っていて、後から直した
- 公開したURLで再生画面が開け、ボタン・再生も動いた。人事の方にURLだけで見てもらえる

## 今回の設計方針

- 通信の作りを、層の分け方・メッセージの定義の置き場所・ECUごとの役割・足しやすさの4つで見直し、そのうち責務のずれ2つ（表示が`can.c`にある、`can.c`が`FaultManager`を知っている）を直した
- `FaultManager`から警告灯データの中身を作る処理は、エンジン監視ECUのモジュールに通信の型を持ち込まないよう、`main.c`の送信タスクに置いた
- 表示の関数は、`meter.c`だけが使うので、このファイルの中だけの関数にし、名前もこのファイルの他の関数に合わせて`meter_`で始めた
- 再生画面をGitHub Pagesで公開し、READMEの案内をURLにした。

- 警告灯データの回転数のビットが、確定状態どおりに送られることを、自動テストで確かめる方法を決める
