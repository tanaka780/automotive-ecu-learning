## 今回の設計方針

- `sim/`へ移したのは置き場所だけで、依存は分かれていない。`main.c`が`sim/`の関数を直接呼ぶので、`sim/`を外すとビルドできない。依存を断つ案（ビルドごとに素通し版へ差し替える）も考えたが、差し替え先になるtarget向けビルドがまだ無いので見送った。Makefileで`ECU_SRCS`と`SIM_SRCS`を分け、この状態が見えるようにした
- イグニッション固定の入口は、乱数のシードを固定する案、乱数で状態を決める処理を`sim/`へ移してから固定を足す案とも比べた。シード固定は「なぜこのシードで全部ONになるのか」がテストから読めず、`rand`の呼び出しが1つ増えるだけで壊れる。`sim/`へ移す案は、`sensor.c`の`rand`を残したまま`ignition`だけ移すことになる
- `ignition_set`は検証用の関数ではない。実車のECUがイグニッション信号を入力として受け取る処理に近く、乱数で決める`ignition_update`の方がシミュレーション側の処理。今は`ignition_update`に手を入れていないので、`previous`を更新する2行が重複している
- 実行関数は最初「3つ目（電源再投入）で共通化する」つもりだった。それでは共通化（既存ファイルの変更）とテスト追加が、電源再投入のときに重なるだけ。先に切り出しだけを行い、既存の11テストが同じ名前でOKのままなのを確かめてから次のテストを足した
- 切り出しでモジュール名での実行が動かなくなり、一度`__init__.py`で直した。ところが、引数なしの`python3 -m unittest`が見つけるテストが0件から11件に変わった。「前に動いていたものが動くか」は確かめたが、「前に動いていなかったものが変わっていないか」を見ていなかった。各テストファイルの先頭で`sys.path`に足す形に戻し、どの実行の仕方でも切り出し前と同じになった
- 故障発生は、`fixture.txt`が実行中ずっと同じ値なので、1サンプル目からCRITICALが続く形でしか再現できない（正常値に戻ってのRecoveredは対象外）。その代わり、`[Sample NN]`ごとに出力を分けて「3サンプル目でDegraded」「`[ALERT]`はサンプル1・2だけ」まで照合した
- 電源再投入の検討中にPhase25の範囲を読み直して、「メーター表示・通信故障は対象外」と決めていたことに気付いた。故障発生のテストのうち`[METER]`を照合する2つがこれに当たる。削るとエンジン監視ECUが送るCANの値を確かめる手段が無くなるので、範囲外と承知で残し、3ECU化で見直すとテストに書いた。メーターECUの通信異常の記録が永続化されないことも、同じ理由で検証していない
- 起動直後のDTCは表示されないので、2回目をOFF固定にした。OFFの間は`diag_check`が呼ばれずDTCが変わらないので、最後の表示がそのまま起動直後の内容になる
- 3回続けて起動して、「再起動後もCRITICALなら発生回数が2になる」「フリーズフレームは上書きされない」という、シナリオに書かれていない動きが見つかった。出力をそのまま仕様に写すと、実装の誤りまで仕様にしてしまう。発生回数は実車でもイグニッションON〜OFFの1サイクルごとに数えるもので、フリーズフレームは「最初の発生時の値」という既存の期待結果と合う。どちらも妥当と判断してから、シナリオの期待結果に加えた。`clear`を挟むと結果が変わるので、流れの3番目に「1回目との間に`clear`は行わない」と書いた
- タスク7で`faultmgr.h`の`#define`を変えたのにテストが落ちず、`sensor_sim`が作り直されていなかったと分かった。Makefileは`.c`だけを依存関係にしているので、`.h`の変更を検知しない。`make clean && make`なら問題ないが、`make scenario`だけだと古い実行ファイルを検証してしまう。Phase25の範囲外なので今回は直さず、既知の制約として記録した
