# Day69

## 実施内容

- `include/uds.h`・`src/uds.c`を新しく作り、エンジン監視ECU役が診断の要求に応答するようにした。記録の件数の読み出し（0x19 01）と全消去（0x14 FFFFFF）に肯定応答を返し、それ以外には否定応答（0x11・0x12・0x13・0x31）を返す。イグニッションOFFの間に届いた要求は読んで捨てる

- `src/main.c`で、スキャンツール役を応答のタスクの後に10ms周期で登録した（計10個）

- `uds.c`の全ての行をテストが通り、入れた7つの誤りはすべて見つかった

## 今回の設計方針

- 応答を作る処理（`uds_handle_request`）は、バイト列を受け取ってバイト列を返すだけにし、busは知らない。busの読み書きとイグニッションの確認は`uds_server_run`に分けた。CANを使わずに、応答の中身だけをテストできる
- 否定応答の判定の順は、サービス→サブファンクションまで読める長さ→サブファンクション→サブファンクションごとの長さ、にした。ISO 14229が決めている順に合わせている
- OFFの間に届いた要求は、読んでから捨てる。読まずに放っておくと、busには最後のフレームが残り続けるので、ONになった瞬間に古い要求（たとえば消去）に答えてしまう。周期のメッセージで`can_monitor_restart`が送信時刻を残すのと同じ問題
- 応答の周期は、Schedulerが周期を見に行く間隔と同じ10msにした。周期を短くしても、ほかのタスクの登録順は変わらないので、出力は変わらない
- 応答の側では、ログを出さない。何を送って何が返ったかは、スキャンツール役が表示する
- 要求を送るタイミングの指定方法で迷った。最初はサンプル番号（`REQ@N`）と起動からのms（`can_fault.txt`の`START_MS`と同じ形）の2つを比べたが、両方とも間違いだと仮定して弱点を挙げ直した。一番大きかったのは、どちらも「送ってすぐ次を送れる」ことだった。busは最新の1フレームしか持たないので、同じサンプルで消去と読み出しを続けて送ると、消去の要求が上書きされて消える。実際のスキャンツールは、1つ送ったら応答を待つ
- 実際の試験スクリプトに近いのは、条件を待ちながら順に送る形だった。ただ、故障を起こすタイミングもイグニッションの切り替えもサンプル番号で決まるので、条件の書き方を新しく作っても結局サンプル番号を待つことになる。送り始めはサンプル番号で決め、送った後は応答を待つ形（案A'）にした
- 案A'も間違いだと仮定して、もう一度見直した。自分の時計からサンプル番号を計算すれば`main.c`の変数を読まずに済むが、それは「サンプルの周期は1000ms」という前提を隠すだけで、周期を変えたときに黙って食い違う。依存するなら、`const`のポインタで読むだけにして、見える形にする。もう1つ、期待する応答もファイルに書いてスキャンツール役が判定する形も考えたが、今は「Cはログを出し、Pythonが期待と比べる」役割分担になっている。期待を2か所に分けないよう、スキャンツール役は表示だけにした
- 指示が無い実行で出力が変わらないことは、Pythonのシナリオ検証には足さず、Phase26と同じく比べるツールで1回確かめた。Pythonの検証には変える前の出力が無く、比べる相手がいない
- `uds_request.txt`が無ければ、読み込みのログも出さない。`can_fault.txt`は無いと`[CAN-FAULT] No CAN fault file`を出すが、ここでログを出すと、今あるすべての実行の出力が変わり、変える前との比べ方が使えなくなる
