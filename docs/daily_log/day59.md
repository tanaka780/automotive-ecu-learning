# Day59

## 実施内容

- `sim/fixture.c`・`sim/fixture.h`で、`fixture.txt`の`TEMP@N=値`の行により、N秒目のサンプル以降の水温を指定できるようにした（実行の途中で水温を変え、冷却ファンのON/OFFを実行で確かめるため）
- `src/main.c`で、`MODE=FIXED`のとき、サンプルごとにその秒の水温へ差し替えるよう配線した
- `test/test_fixture.c`に、`TEMP@N`行の読み込みと切り替えを確かめる7テストを足した
- `scenario_test/test_fan_control.py`を追加した（冷却ファン制御・水温センサ故障時の冷却ファン制御を、仮想時間版で秒単位まで照合する11テスト）
- `scenario_test/sensor_sim_runner.py`で、実行する実行ファイルを選べるようにした（既定は実時間版のまま）

## 確認内容

途中で水温を変える仕組み

- `TEMP@N`行が無いとき、出力が変更前と変わらないか（仮想時間版の8条件で全文を比べる）
- `TEMP@N`行で決めた秒に水温が変わり、それがファン制御ECUとメーターECUに届くか。実時間版と仮想時間版で同じになるか
- 新しい単体テストが、わざと入れた誤りで落ちるか

ファンの期待結果の自動テスト

- 実行前に書き出した予想（ファンが切り替わる秒、メーターに届く秒と値、故障の確定・復帰の秒、メーターが受け取る水温）と、仮想時間版の出力が合うか
- 新しいテストが、わざと入れた誤り（Day58で直す前のファン制御ECU、閾値の変更、ヒステリシスなし）で落ちるか
- 既存の単体テスト・シナリオ検証が変わらず通るか

READMEの図

- 「実際に動かした結果」の図の元にする条件で、予想した流れ（4秒目ファンON → 9秒目に異常と判断 → 15秒目に回復 → 16秒目ファン停止）になるか
- 図の文字が重ならず、図からはみ出さないか。白い背景で、GitHubのライト／ダークモードの背景色でも読めるか
- 書いた手順どおりに、図を作り直せるか

## 判定

途中で水温を変える仕組みも、ファンの期待結果のテストも、予想どおりに動いた。

- `TEMP@N`行が無い8条件は、変更前と全文一致し、既存の動作は変わっていない。終了コードは全文比較では見ていないが、実時間版の`make scenario`（最後まで実行されたかを確かめるテストを含む）で確かめた
- `TEMP@N`行がある実行では、水温・ファン・メーターの表示が、実時間版と仮想時間版で同じになった。80℃でON、75〜80℃の間はONを保持、75℃でOFF、間の79℃ではOFFのまま、という冷却ファン制御の期待結果どおり
- 新しいシナリオテストは、実行前に書き出した予想と全項目で一致し、わざと入れた4種類の誤りではどれも関係するテストだけが落ちた
- Day58で直した復帰の瞬間の誤りは、このテストで見張れる。確定の瞬間の一瞬OFFは、タスクの開始がずれたときしか起きないので見張れず、単体テストに任せている
- `TEMP@N`行を、ランダムなイグニッション（途中に電源OFFの秒がある）や`MODE=RANDOM`と組み合わせた場合は、コードで確かめただけで、実行していない。サンプル番号は電源OFFの秒も数えるので「N秒目以降」の意味は変わらず、`main.c`は`MODE=FIXED`のときしか差し替えない
- 最初は、水温センサ故障の条件にだけ「通信の途絶が記録されていない」確認を入れ忘れていて、再確認で`test_no_link_lost`を足した
- READMEの図は、予想どおりの流れの出力から描け、測った13枚とも文字の重なり・はみ出しは無かった。ただし、GitHub上での見え方（特に日本語の文字）は、まだpushしていないため確かめていない。ただし最初は3か所で重なり（点線のラベルと温度の値、ランダムの図の温度の値どうし・ファンの帯の言葉どうし）、直してから測り直した。温度の値の間隔の判定は、最初の14pxでは日本語の文字の高さ（約17px）に足りず、18pxに直した
- 図の9秒目の言葉に、最初は「判断・記録」と書いていた。記録（故障の回数とフリーズフレーム）は危険な値になった7秒目で、9秒目は判断だけなので、「記録」を外した。言葉を置く秒は出力から決まっても、言葉の中身は手で書いたものなので、ずれうる
- 実時間版の比較スクリプトは、基準（Day58に`/tmp`へ取った出力）が消えていて、取り直すと約11分かかるため行っていない。仮想時間版の全文比較と実時間版の`make scenario`で、変わっていないことを確かめた

## 今回の設計方針

- 時刻はミリ秒ではなくサンプル番号で指定した。センサ値は1秒に1回しか読まないので秒で足り、実時間版でも毎回同じサンプルで切り替わる。`can_fault.txt`がミリ秒なのは、200ms周期のメッセージのずれを試すため
- 途中で変えられるのは水温だけにした。今の目的は冷却ファンの確認だけで、必要になれば同じ形で`SPEED@N`などを足せる
- 置き場所は新しいファイルに分けず、`fixture.c`に足した。どちらも「センサの値を外から差し込む」という同じ役割で、ファイルの読み方と値域チェックを使い回せる
- サンプルごとに行を分ける関数は、`test_fault_occurrence.py`と同じものを新しいファイルにも置いた。使う場所が2か所のうちは共通化しない
- READMEの冒頭に、転職面接で人事の方に「どんなプログラムを作ったか」を見せるための節（構成図、実際に動かした結果の図、できることの表、取り組みの量、工夫したこと）を置いた。見せる相手が人事の方なので、図は日常の言葉だけで描き、何を作ったか（構成と1回の動き）を見せることを中心にした。図2枚と短い説明だけでは取り組みの量が伝わらないため、扱っている対応の一覧と数字も添えた
- 図の元の条件は、Day59のテストの条件（95℃から始まる）を使わず、新しく作った。95℃を「熱いのでファンを回す」と「センサー異常と判断する」の両方に使うと話が食い違うため、普段の温度 → 熱くなる → 危険な値が続く → 戻る → 冷える、の順にした。危険な値が3回続いたらセンサーを信用しないというのは、このプログラムの簡略化で、実車では過熱とセンサー故障を見分ける工夫が要る
- 図はSVGにし、Python標準ライブラリだけで描いた（今の環境にmatplotlibは無い）。横軸は1秒単位（出力に時刻が無い）、白い背景（GitHubのダークモードで透明だと黒い文字が読めない）、日本語フォントを指定した。図の元の条件は`tools/fan_run_example_fixture.txt`に残し、作り直せるようにした
- 再生画面（メーター風のGUI）は、図とREADMEの文章を先に仕上げてから作る。人事の方との面接では画面を見せられるとは限らず、画面が無くても伝わる説明を先にそろえるため
